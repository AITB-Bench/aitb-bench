The Sovereign AI Horizontal Memory (SAIHM) Protocol
 draft-saihm-memory-protocol-03
Abstract 
This document defines the Sovereign AI Horizontal Memory (SAIHM)
 protocol, a memory layer for AI agents. A SAIHM operator stores an
 agent's memory as encrypted cells bound to a post-quantum holder
 identity, records each state change in a public audit log, and
 supports revocable sharing contracts. The protocol defines an
 erasure operation with two stated erasure classes, intended to help
 an operator meet its obligations under Article 17 of EU Regulation
 2016/679 (GDPR).
This revision specifies the custodial profile. The operator holds
 the holder's keys and performs all cryptography. The agent-side
 client holds no keys, runs no cryptography beyond TLS and keeps no
 store; it reaches the operator over HTTPS and exposes the protocol to
 the agent as eight Model Context Protocol (MCP) tools. The document
 defines the operator obligations, the HTTPS binding, the eight tools,
 and the checks a conformant client applies to what the operator
 returns.

1. Introduction
This document is published through the Independent Submission Stream
 of the RFC Series, as defined in [RFC4846] and described in
 [RFC8730]. It is not an Internet Standard, and it has not been
 reviewed for, nor does it necessarily reflect, the rough consensus of
 the IETF community.
1.1. Motivation
The Model Context Protocol [MCP], donated to the Agentic AI
 Foundation [AAIF] under the Linux Foundation on 9 December 2025,
 defines how an AI agent reaches external tools and contextual data
 sources. It does not standardize how an agent persists memory across
 sessions, models, or vendors. Here, "memory" means the holder's
 content-addressed cells (Section 2.1; Section 1.4).
Production agents today keep memory in a local file system, a vendor-
 specific session log, or a vector database. None of these gives a
 signed record of each memory and of each change to it, a public log
 of those changes, or an erasure operation with stated properties
 ([GDPR], Article 17).
SAIHM is a memory-layer protocol that an MCP-capable agent attaches
 to obtain durable, shareable and erasable memory. Nothing in it
 depends on a particular operator or vendor.

1.2. The custodial profile
This document specifies the custodial profile, in which the operator
 generates and holds the holder's identity key and every data-
 encryption key, encrypts on write, decrypts on read, signs cells and
 receipts on the holder's behalf, and returns plaintext to the
 authenticated holder.
The client in this profile forwards each tool call to the operator
 over HTTPS, holds no key material, and validates the shape of each
 response before reporting it to the agent (Section 7). Its security
 rests on the transport and on the operator, and Section 8 states what
 that does and does not protect.
A profile in which the holder keeps the keys and the operator sees
 only ciphertext is possible under the same cell shape. It is outside
 the scope of this revision.
1.3. Scope
This document defines:
* The cell shape: an encrypted memory unit with canonical metadata.
* Holder identity bound to an ML-DSA-65 key pair ([FIPS204]) derived
 through HKDF ([RFC5869]).
* The encryption envelope, with a random per-cell data-encryption
 key wrapped under a versioned key-encryption key.
* Receipts recorded in a public audit log.
* Sharing contracts in three modes: temporary, permanent and
 syndicate.
* Two erasure classes, cryptographic and access-control, and the
 obligation on an operator to state which it provides.
* An HTTPS binding between the client and the operator.
* An MCP binding of eight tools, and the checks a client applies to
 each tool's result.
This document does NOT define:
* How the operator stores ciphertext, or which audit log it uses.

* How the operator authenticates the holder. The client carries an
 operator-defined credential and treats it as opaque.
* Vector-database or retrieval-ranking semantics.
* Agent runtime semantics, which MCP and its host runtimes cover.
1.4. Conventions and Terminology
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
 "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
 "OPTIONAL" in this document are to be interpreted as described in BCP
 14 [RFC2119] [RFC8174] when, and only when, they appear in all
 capitals, as shown here.
AEAD: Authenticated Encryption with Associated Data ([RFC5116]).
 AES-256-GCM ([NIST-SP-800-38D]) is RECOMMENDED.
Cell: an encrypted memory unit (Section 2.1).
Client: the software on the agent's side that exposes the eight
 SAIHM tools to an MCP host and forwards each call to the operator
 endpoint. In the custodial profile the client holds no key
 material.
Custodial operator: an operator that holds the holder's identity key
 and the data-encryption keys and performs all cryptographic
 operations on the holder's behalf.
DEK: Data Encryption Key. A 32-byte symmetric key, unique to one
 cell, used with the AEAD cipher.
Endpoint: the HTTPS URL at which an operator accepts tool calls
 (Section 3).
HKDF: HMAC-based Extract-and-Expand Key Derivation Function
 ([RFC5869]), instantiated with SHA-256.
holder seed: a secret of at least 256 bits from which a holder's
 identity key is derived (Section 2.2). In the custodial profile
 the operator generates and holds it.
Holder: the natural person, organization, or autonomous agent on
 whose behalf cells are written. Each holder has one holderId.
KEK: Key Encryption Key. An operator-held key that wraps DEKs. Each
 KEK generation has a 32-bit version number, kekVersion.

MCP: the Model Context Protocol [MCP]. In MCP, a "tool" is a named
 operation with typed inputs and typed outputs that an MCP server
 exposes to a model.
memory: the set of SAIHM cells bound to one holderId, less those
 that have been erased. This is distinct from memory in the
 computer-architecture sense.
ML-DSA: Module-Lattice-Based Digital Signature Algorithm
 ([FIPS204]). SAIHM uses the ML-DSA-65 parameter set.
Operator: the party that runs an endpoint and provides storage,
 cryptography, audit logging and access control to holders.
Receipt: a signed record of one operation, written to the public
 audit log (Section 2.5).
Result identifier: the identifier an operator returns to name the
 object a write produced or acted on: a cellId, contractId or
 proposalId (Section 4.1). It is distinct from receiptId, which
 names an audit-log entry.
sentinel value: an in-band value that signals the absence of an
 ordinary value of the same type. In Section 2.6, an expiry of 0
 means "no time bound".
Shard: a cell as stored under a storage tier. A shard is named by
 its cellId, and sharing contracts list the cellIds they cover.
storage tier: a named, operator-chosen persistence class with stated
 durability and retention properties. Tier names carry no protocol
 semantics.
UNIX epoch: the time reference defined in [IEEE-1003.1-2024] under
 "Seconds Since the Epoch". SAIHM timestamps are unsigned integer
 seconds since the UNIX epoch.
1.5. Substrate prerequisites
A conformant operator depends on the following. Where a substrate is
 selected per deployment, the operator states its selection in its
 published documentation.
(a) A source of random bits suitable for key generation ([RFC4086]).
(b) HKDF with SHA-256 ([RFC5869], [FIPS180-4]).
(c) ML-DSA-65 conformant with [FIPS204].
Jackson Expires 14 April 2027 [Page 6] 
 Internet-Draft SAIHM Protocol October 2026 
(d) An AEAD cipher conformant with [RFC5116]; AES-256-GCM is
 RECOMMENDED.
(e) SHA-256 ([FIPS180-4]) for cellId derivation.
(f) A CBOR codec ([RFC8949]) for cells and receipts at rest.
(g) An HTTPS server ([RFC9110] over [RFC9846]) for the endpoint.
(h) A public, append-only audit log in which any party can fetch an
 entry by its identifier and list entries by subjectId, by
 holderId and by operation (Section 2.5). Selected per
 deployment.
(i) A storage tier offering put, get and delete over opaque
 ciphertext. Selected per deployment.
A conformant client depends on an MCP server runtime, an HTTPS
 client, and a JSON parser ([RFC8259]). It needs no cryptographic
 library beyond the one its TLS stack uses.
2. Architecture
2.1. Cell shape
A SAIHM cell is the tuple:
<cellId, holderId, kekVersion, tier, cellNonce, ciphertext,
 signature, timestamp>
cellId: 32-byte content-derived identifier, computed as
cellId = SHA-256( kekVersion_be32 ||
 cellNonce ||
 ciphertext )
where kekVersion_be32 is kekVersion as a 4-byte big-endian
 unsigned integer, ciphertext is the full AEAD output including the
 authentication tag, and || is octet concatenation. On the wire
 cellId is a lowercase hexadecimal string of 64 characters.
Because kekVersion and cellNonce are inputs, the same plaintext
 written twice yields two distinct cellIds.
When the operator reads a cell it MUST recompute cellId from the
 stored kekVersion, cellNonce and ciphertext, and MUST refuse to
 serve a cell whose stored cellId does not match.
Jackson Expires 14 April 2027 [Page 7] 
 Internet-Draft SAIHM Protocol October 2026 
holderId: 32-byte holder identifier: the SHA-256 digest of the
 holder's ML-DSA-65 public key (Section 2.2). On the wire it is a
 64-character lowercase hexadecimal string.
kekVersion: 32-bit unsigned integer naming the KEK generation in
 force when the cell was written. It is fixed for the life of the
 cell; later re-wrapping of the DEK does not change it
 (Section 2.4).
tier: short ASCII string naming the storage tier.
cellNonce: 16 random bytes, unique per cell. cellNonce is public and
 travels with the cell.
ciphertext: the cell payload encrypted under the cell's DEK.
signature: ML-DSA-65 signature made with the holder's identity key
 (Section 2.3).
timestamp: 64-bit unsigned integer, UTC seconds since the UNIX
 epoch. Implementations MUST NOT use a 32-bit signed
 representation, which overflows at 03:14:07Z on 19 January 2038.
2.2. Identity binding (ML-DSA-65)
A holder's identity key is derived from the holder seed:
identityKey = HKDF-SHA-256(salt = "MPS-PQC-KEY-GEN-v1",
 IKM = holderSeed,
 info = "MPS-AGENT-IDENTITY-v1",
 L = 64 bytes)
The first 32 bytes of identityKey are the seed (xi) for ML-DSA-65 key
 generation ([FIPS204], ML-DSA.KeyGen_internal). The remaining 32
 bytes are reserved. holderId is SHA-256 of the resulting public key.
In the custodial profile the operator generates the holder seed,
 derives the key pair, and holds the private key. The private key and
 the holder seed MUST NOT be sent to the client, written to a receipt,
 or returned by any tool. The operator signs each cell and each
 receipt with the holder's private key after it has authenticated the
 caller as that holder (Section 3.2).
Jackson Expires 14 April 2027 [Page 8] 
 Internet-Draft SAIHM Protocol October 2026 
When it creates a holder, the operator MUST write the holder's public
 key to the audit log in a KEY receipt (Section 2.5), which anyone can
 find by holderId. The holder cannot be used until that receipt is
 written. With that entry, anyone can check every receipt signature
 for the holder without the operator's help, and anyone given a cell
 can check the cell signature.
2.3. Signed messages
Every signature in this protocol is ML-DSA-65 in its pure form (ML-
 DSA.Sign, [FIPS204]) with a context string that names what is signed,
 so that a signature over one kind of message cannot be presented as
 another:
Cell, context "SAIHM-CELL-v1": cellId || holderId ||
 kekVersion_be32 || timestamp_be64, where timestamp_be64 is
 timestamp as 8 bytes, big-endian.
Receipt, context "SAIHM-RECEIPT-v1": the deterministic CBOR encoding
 ([RFC8949], Section 4.2.1) of the receipt map (Section 5) without
 keys 1 (receiptId) and 5 (signature). receiptId is SHA-256 of the
 same bytes.
Contract, context "SAIHM-CONTRACT-v1": the deterministic CBOR
 encoding of the contract map (Section 5) without keys 1
 (contractId) and 9 (signature), and including key 10
 (contractNonce). contractId is SHA-256 of the same bytes.
An operator MAY use the hedged (randomized) or the deterministic
 signing variant.
2.4. Encryption envelope
For each new cell the operator:
1. draws a fresh 32-byte DEK and a fresh 16-byte cellNonce from its
 random source;
2. encrypts the payload under the DEK with the AEAD cipher;
3. wraps the DEK under the current KEK generation and stores only
 the wrapped form, keyed by cellId;
4. discards the unwrapped DEK once the write completes.
Jackson Expires 14 April 2027 [Page 9] 
 Internet-Draft SAIHM Protocol October 2026 
The DEK MUST be independent of every other key the operator holds.
 In particular it MUST NOT be derivable from identityKey, from the
 holder seed, or from any other long-lived secret. Cryptographic
 erasure (Section 2.7) depends on this (Section 8.6).
The AEAD nonce (for AES-256-GCM, the 96-bit IV) is chosen by the
 operator and MUST NOT repeat under one DEK. Because each DEK
 encrypts one payload, using the first 12 bytes of cellNonce is
 sufficient, and the example in Appendix B.2 does so. The cell does
 not name its AEAD algorithm or the key-wrap algorithm; both are
 operator-internal and stated in the operator's documentation.
No associated data is used. The ciphertext is bound to the cell by
 cellId and by the cell signature, and the operator MUST check both
 before it decrypts (Section 4.3).
KEK rotation is versioned. An operator MAY rotate the KEK under its
 own policy and MAY re-wrap existing DEKs under the new generation.
 The wrapped DEK is stored with the version of the KEK that wrapped
 it, apart from the cell, so re-wrapping changes neither cellId nor
 the cell signature. An operator MUST re-wrap every DEK held under a
 KEK generation before it retires that generation.
2.5. Audit log
For each operation that needs one (Section 6, and the KEY receipt of
 Section 2.2) the operator writes a receipt:
<receiptId, subjectId, operation, holderId, signature, timestamp,
 receiptNonce [, detail]>
subjectId is the cellId, contractId or proposalId the operation acted
 on, or the holderId for KEY, RECALL and STATUS receipts. operation
 is one of "KEY", "REMEMBER", "RECALL", "STATUS", "FORGET", "SHARE",
 "REVOKE", "PROPOSE" or "VOTE". A KEY receipt also carries the
 holder's ML-DSA-65 public key, a PROPOSE receipt carries the
 proposal, and a VOTE receipt carries the vote's direction and weight.
 Every receipt carries 16 random bytes, receiptNonce, so that two
 otherwise identical receipts have different receiptIds.
Jackson Expires 14 April 2027 [Page 10] 
 Internet-Draft SAIHM Protocol October 2026 
The receipt is written to a public, append-only audit log. The log
 MUST let any party fetch an entry by its receiptId and list entries
 by subjectId, by holderId and by operation (for example all VOTE
 receipts for a proposalId, a holder's KEY receipt, or every FORGET
 receipt), so that a third party holding a receiptId can check the
 receipt's signature against the holder's public key. An operator
 SHOULD return the receiptId in the result of every state-changing
 tool, as the member "receiptId"; saihm_forget returns it as
 destructionAnchor. The choice of log is a deployment decision.
2.6. Sharing contracts
A holder MAY grant other agents access to some of its shards through
 a sharing contract:
<contractId, holderId, granteeIds, shardIds, mode, scope,
 expiresAt, timestamp, signature, contractNonce>
granteeIds is a non-empty list of 32-byte holderIds with no
 duplicates; the operator MUST reject any entry of another length.
 shardIds is a non-empty list of the holder's cellIds that the
 contract covers; nothing outside it is exposed, and the contract does
 not copy the cells.
scope is "read", "write" or "readwrite". This revision defines only
 "read", which lets a grantee receive the covered cells from
 saihm_recall. None of the eight tools lets a grantee write into
 another holder's memory, so an operator MUST reject "write" and
 "readwrite" with the error "invalid_scope". They are reserved for a
 later revision.
mode is one of:
TEMPORARY: revocable; expiresAt MUST be later than the contract
 timestamp and no later than the contract timestamp plus 86400
 seconds. The sentinel 0 is not permitted.
PERMANENT: revocable; expiresAt MUST be the sentinel 0 (no time
 bound).
SYNDICATE: revocable; intended for a fixed group of grantees that
 share one grant and lose access together, such as an incident-
 response team. expiresAt MAY be 0 or a future timestamp.
 SYNDICATE differs from the other modes only in this intent and in
 its expiry rule.
contractNonce is 16 random bytes.
Jackson Expires 14 April 2027 [Page 11] 
 Internet-Draft SAIHM Protocol October 2026 
Any holder can name any holderId as a grantee, since holderIds are
 public. A contract therefore takes effect for a grantee only after
 that grantee has accepted it, by a means the operator provides
 outside this binding. An operator MAY treat contracts between
 holders it has linked in advance, such as holders of one
 organization, as accepted. A grantee MUST be able to decline or
 later withdraw its acceptance (Section 8.5).
A contract is active for a grantee while it is accepted by that
 grantee, not revoked, and its expiresAt is 0 or later than the
 current time.
On saihm_recall by a grantee, the operator MUST include the covered
 cells of every active contract that names the grantee, and MUST NOT
 include a cell whose only grant to that grantee is a contract that is
 not active for that grantee.
Revocation takes effect for every grantee of the contract as soon as
 the operator applies it (Section 2.8). It governs future reads only.
 Content a grantee has already received is outside its reach.
2.7. Erasure
saihm_forget erases one cell. Every conformant operator MUST, on a
 successful erasure:
1. stop serving the cell to the holder and to every grantee, under
 every contract;
2. write a FORGET receipt for the cellId to the audit log;
3. add the cellId to its erasure list, a public, append-only set of
 erased cellIds that matches the FORGET receipts in the audit log
 once any pending receipt is written (Section 2.8), so that any
 observer can rebuild it.
An operator MUST consult the erasure list on every saihm_recall and
 MUST NOT return an erased cell to anyone.
Beyond those steps an operator provides one of two erasure classes:
Cryptographic erasure: the operator also destroys every copy of the
 cell's wrapped DEK, including copies in backups and replicas.
 Because the DEK is random and wrapped only for this cell
 (Section 2.4), the ciphertext then cannot be decrypted by anyone,
 the operator included, wherever copies of it remain.
Access-control erasure: the cell is withdrawn from service as above,

2.8. Order of effect and receipt
For saihm_forget and saihm_revoke_share the operator MUST withdraw
 access before it writes the receipt, and MUST NOT restore access if
 the receipt write fails. If it cannot withdraw access it answers
 "operator_storage_unavailable" and nothing has changed. It retries
 the receipt until it is written. Until then it answers with the
 error "operator_log_unavailable", which here means that access has
 been withdrawn and the receipt is pending. A repeated
 saihm_revoke_share then returns revoked = true, and a repeated
 saihm_forget returns success = false (already erased). A client that
 receives this error SHOULD tell the agent that access may already be
 withdrawn and that repeating the call shows the outcome.
For the other state-changing tools the operator first stores the
 effect durably but invisibly, then writes the receipt, then makes the
 effect visible. If the effect cannot be stored or the receipt cannot
 be written, the operator discards the effect (no cell is stored, no
 contract or proposal takes effect, no vote is counted) and answers
 "operator_storage_unavailable" or "operator_log_unavailable"; for
 these tools both errors mean that no receipt was written and nothing
 took effect. If the operator cannot tell whether a receipt write
 succeeded, it MUST look the receipt up by its receiptId before
 answering, and treats a receipt it finds as written. Once the
 receipt is written the operator MUST complete the effect, including
 after a restart, and answers only with the success result carrying
 the result identifier.
3. HTTPS binding
3.1. Request and response
The client sends each tool call to the endpoint as one HTTP POST
 ([RFC9110]) with these headers:
* Content-Type: application/json

* Authorization: the operator-issued credential, sent verbatim.
The request body is a JSON object with two members:
{"method": "<tool name>", "params": { ... }}
method is one of the eight tool names in Section 4. params carries
 the operator parameters listed for that tool.
On success the operator answers with a 2xx status and a JSON body
 that is the tool's result object (or, for saihm_recall, an array).
 There is no outer envelope. On failure it answers with a 4xx or 5xx
 status; it SHOULD include a JSON body {"error": "<code>"} using the
 codes listed per tool. An operator that does not enable a tool (for
 example, governance) MUST answer that tool with a failure status.
A JSON integer that can exceed 2^53 - 1 (epochs, weights, counts)
 SHOULD be sent as a decimal string. A client MUST accept either a
 JSON number or a decimal string for every numeric field, and MUST
 accept true, false, "true", "false", 1, 0, "1" and "0" for every
 boolean field.
Fields not defined here are operator extensions. A client MUST
 ignore an extension it does not recognize, and an operator MUST NOT
 rely on a client displaying one.
Hexadecimal values are base16 ([RFC4648], Section 8) in lowercase. A
 cellId, holderId, contractId, proposalId or receiptId (including
 destructionAnchor) is 64 hexadecimal characters.
A client MAY report only the status code of a failure and not its
 body; the error codes below are for operators, logs and clients that
 read them.
3.2. Authentication
The operator authenticates the caller from the Authorization header
 under a scheme it defines, for example a bearer token issued to one
 holder. The client treats the value as opaque and MUST NOT place
 private key material in it. The client does not sign requests; in
 the custodial profile the holder's signature on cells and receipts is
 made by the operator, after authentication, with the holder's
 custodied key.

A client:

* MUST refuse an endpoint whose scheme is not https, except http to

4.10. Governance form
This protocol defines the two governance tools but not a single
 governance form. An operator that enables governance MUST publish,
 at a stable URL, at least:
(a) eligibility to propose;
(b) eligibility to vote;
(c) the vote-weight function, evaluated at the proposal's snapshot
 epoch, so that weight acquired after the snapshot does not
 count;
(d) the threshold for a proposal to pass;
(e) the voting window, in seconds;
(f) the permitted proposal scopes and, for each, the parameters it
 may change.
Tallies MUST be reproducible from the VOTE receipts in the audit log,
 counting, for each holder and proposal, only the first VOTE receipt
 in log order. Where two PROPOSE receipts carry the same proposalId,
 the first in log order governs.

6. Receipt semantics
For each call that changes state (saihm_remember, saihm_forget,
 saihm_share, saihm_revoke_share, saihm_governance_propose,
 saihm_governance_vote) the operator MUST write a receipt to the audit
 log carrying the operation, the subjectId, the holderId and the
 timestamp, signed with the holder's key (Section 2.3). A call that
 changes nothing, such as a repeated vote (Section 4.9) or a repeated
 saihm_forget or saihm_revoke_share, writes no receipt.
A receipt MUST NOT contain plaintext, a DEK, a wrapped DEK, a KEK,
 the holder seed or a private key. A FORGET receipt carries the
 erased cellId as its subjectId.
Read-only calls (saihm_recall, saihm_status) MAY produce receipts
 under operator policy, under the same content restrictions.

8. Security considerations
8.1. Trust in a custodial operator
In the custodial profile the operator holds every key and sees every
 plaintext. Encryption at rest protects against theft of stored
 ciphertext and of backups, and against a storage provider separate
 from the operator. It does not protect a holder's content from the
 operator itself. That protection requires a profile in which the
 holder keeps the keys.
Jackson Expires 14 April 2027 [Page 26] 
 Internet-Draft SAIHM Protocol October 2026 
The holder's signatures are made by the operator. They establish
 that the operator, having authenticated the caller as that holder,
 wrote the cell or receipt. They do not prove that the holder's own
 machine produced it.
The operator MUST protect the holder seeds, identity keys and KEKs it
 holds at least as strongly as the plaintext they protect, and SHOULD
 keep KEKs in hardware or a separate key service.
8.2. Post-quantum signatures
Cells and receipts are signed with ML-DSA-65 ([FIPS204]), a NIST-
 standardized post-quantum signature algorithm, chosen so that
 receipts resist forgery by an adversary with a cryptographically
 relevant quantum computer. This does not extend to the operator's
 custody of the keys, or to the audit log's own integrity mechanism,
 whose algorithms are chosen by the deployment. TLS key exchange
 SHOULD include a post-quantum or hybrid group where both ends support
 one.
8.3. Credential handling
The Authorization value is a bearer credential for the holder's
 memory. A client MUST NOT echo it, or an endpoint value that may
 contain it, into tool output, including in errors raised by its HTTP
 library when the value is malformed (Section 3.3). Operators SHOULD
 issue credentials scoped to one holder, with an expiry, and
 revocable.
8.4. Hostile or faulty responses
A client cannot assume the endpoint is the operator. A misconfigured
 URL, a proxy or an attacker on a weakened transport can answer
 instead. The checks in Section 7 limit what such a responder can
 make the agent believe. In particular, the result-identifier rule
 (Section 4.1), the control-character rule (Section 7) and the framing
 rule for recall plaintext (Section 7) together keep a single response
 from adding a forged report entry, the erasure rule prevents an
 acknowledgement without an identifier from being reported as an
 erasure, and the redirect rule keeps plaintext from leaving for an
 unchecked host.

8.5. Unsolicited shares
A sharing contract places another holder's text in the grantee's
 recall, which an agent loads at the start of a session. Under
 Section 2.6 a holder can do this only after the grantee has accepted
 the contract, or where the operator has linked the two holders in
 advance. Accepted shared text is still written by another holder.
 The client marks it (Section 7), and an agent should not follow
 instructions found in it.
8.6. Erasure properties
Cryptographic erasure holds only if no copy of the DEK, and nothing
 it can be derived from, survives. This is why the DEK is random and
 independent of identityKey (Section 2.4). An operator that derived
 DEKs from a long-lived secret could re-derive a deleted DEK and
 decrypt, so it would provide access-control erasure at most.
Plaintext the operator returned to the holder before erasure, and
 plaintext a grantee received, are outside the operator's control, and
 erasure does not affect them.
9. Privacy considerations
9.1. GDPR Article 17
saihm_forget gives a holder an erasure operation with a receipt in a
 public log and an entry in a public erasure list. Whether it also
 makes retained ciphertext unreadable depends on the erasure class the
 operator states (Section 2.7). The protocol does not by itself make
 an operator compliant. Operators acting as controllers or processors
 under [GDPR] remain responsible for erasure without undue delay,
 including any plaintext in logs, caches and backups, and handle a
 request from a data subject who is not the holder outside this
 protocol.
Erasure leaves the cell's receipts and its erasure-list entry in
 place. The receipts carry the holderId and the erasure-list entry
 carries the cellId. Before choosing a public log, an operator
 assesses whether holderIds are personal data in its deployment and,
 if so, uses separate holderIds per context or a log whose entries it
 can restrict.
Jackson Expires 14 April 2027 [Page 28] 
 Internet-Draft SAIHM Protocol October 2026 
9.2. Recall queries
Because the operator decrypts, it also receives each recall query;
 draft-saihm-memory-protocol-01 kept the query on the holder's side.
 A query can reveal what the agent is working on even when it matches
 nothing. Operators SHOULD NOT log query text, and MUST NOT write it
 to a receipt.
9.3. Audit log content
Receipts are public. They show that a holderId performed an
 operation on a subject at a time, but not memory content. The
 existence and timing of a holder's cells are therefore observable.
 PROPOSE receipts disclose the proposal, VOTE receipts disclose each
 vote's direction and weight, and an operator that writes RECALL or
 STATUS receipts discloses when the holder reads. Where that is
 sensitive, further measures outside this protocol apply, such as
 separate holder identities per context.

Appendix C. Changes from draft-saihm-memory-protocol-01 
* Specifies the custodial profile: the operator holds the keys and
 performs all cryptography; the client holds none.
* Adds the HTTPS binding between client and operator, and removes
 per-call request signing by the client.
* Replaces the HKDF-derived DEK with a random per-cell DEK wrapped
 under the KEK, so that an operator holding the identity key can
 offer cryptographic erasure.
* Sends the recall query to the operator, which decrypts and
 filters.
* Reports a missing or erased cell in saihm_forget as success =
 false, makes revocation idempotent, and revises the error codes.
Jackson Expires 14 April 2027 [Page 35] 
 Internet-Draft SAIHM Protocol October 2026 
* Defines the signed messages with ML-DSA context strings, adds KEY
 receipts carrying the holder's public key, and defines the
 contract encoding.
* Restricts TEMPORARY expiry, defines shardIds as cellIds, reserves
 the write scopes, and states the order of effect and receipt for
 every state-changing tool.
* Moves the bfsi computation to the holder.
* Requires grantee acceptance before a contract takes effect, the
 owner's holderId on every recalled cell, and the marking of cells
 shared by another holder.
* Defines two erasure classes and requires the operator to state
 which it provides.
* Brings each tool's inputs and results into line with the
 implementation in Appendix A: share takes grantee and shard lists,
 a lowercase type and an access scope; vote takes a boolean;
 governance is optional for operators.
* Adds result identifiers, client conformance checks, and MCP tool
 annotations.
* Defines holderId as SHA-256 of the ML-DSA-65 public key, and the
 key-generation seed as the first 32 bytes of identityKey.
* Generalizes the audit anchor to a public append-only audit log,
 and leaves the storage tier and log to the deployment.
* Replaces the example signature prefix with a deterministic,
 reproducible value, and gives the example inputs in hexadecimal.
